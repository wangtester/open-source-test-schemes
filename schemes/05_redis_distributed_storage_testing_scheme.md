# Redis 自动化测试方案与用例设计深度剖析

## 1. 项目背景与系统架构特征

### 1.1 系统定位与技术栈
[Redis](https://github.com/redis/redis) 是全球应用最广的高性能分布式内存键值数据库。系统采用纯 C 语言编写，核心采用单线程事件循环与 I/O 多路复用模型，支持主从复制、Sentinel 自动故障转移、Redis Cluster 分布式分片以及 RDB/AOF 磁盘持久化。

### 1.2 被测系统核心组成
1. **Server 内核与命令处理引擎**：负责 RESP 协议解析、字典与跳表数据结构操作、过期淘汰与内存逐出策略。
2. **持久化系统（RDB / AOF / AOF Rewrite）**：后台子进程执行 Copy-on-Write 磁盘快照与追加写日志重写。
3. **高可用与分布式组件（Replication / Sentinel / Cluster）**：长连接同步流、心跳探测、Gossip 协议、主从切换与分布式重定向。
4. **原子脚本与事务（Lua Engine & Multi/Exec）**：事务原子执行保障。

### 1.3 自动化测试的主要难点与挑战
* **C 语言内存安全隐患**：缓冲区溢出、野指针、内存越界读取与内存泄漏是核心系统致命威胁。
* **分布式并发时序与网络异常模拟**：主从网络分区、网络延迟、脑裂、节点突发宕机等真实极端网络环境的重现极难。
* **数据持久化与断电容错验证**：如何测试写入过程中操作系统突发断电、AOF 日志截断残损时的自愈能力。

## 3. 核心功能及测试用例设计剖析

### 3.1 功能一：基于 Tcl 夹具的动态多实例与拓扑管理

#### 3.1.1 业务功能背景
Redis 测试需要随时启动 1 个 Master + 2 个 Slave + 3 个 Sentinel 的复杂集群，并在测试完成后保证所有进程被绝对安全回收。

#### 3.1.2 测试用例设计方案
Redis 在 `tests/support/server.tcl` 中封装了动态 Server 生成器：
* 自动分配随机未占用端口。
* 动态渲染生成专有的 `redis.conf`。
* 启动后台 `redis-server` 进程并等待就绪握手。
* 注入 Tcl 钩子，用例结束自动发送 `SHUTDOWN NOSAVE` 并删除临时持久化文件。
* **Tcl 测试用例示例**：
```tcl
start_server {tags {"replication"}} {
    set master [srv 0 client]
    set master_port [srv 0 port]
    
    # 在主节点后启动从节点
    start_server {} {
        set slave [srv 0 client]
        $slave replicaof 127.0.0.1 $master_port
        
        # 等待同步完成
        wait_for_condition 50 100 {
            [status $slave role] eq "slave" &&
            [status $slave master_link_status] eq "up"
        } else {
            fail "Replication link failed to come up"
        }
    }
}
```

### 3.2 功能二：主从增量同步与断网重连（PSYNC / Backlog）测试

#### 3.2.1 业务功能背景
当主从节点之间的网络瞬时断开后，从节点重新连接时，应该利用内存积压缓冲区（Replication Backlog）进行快速增量同步（Partial Resynchronization），而非昂贵的全量 RDB 传输。

#### 3.2.2 测试用例设计方案
* **测试用例编排步骤**：
  1. 建立 Master-Slave 关系，写入数据 `set k1 v1`。
  2. 模拟网络中断：通过发送 `CLIENT PAUSE` 命令或直接关闭从节点连接。
  3. Master 继续写入 1000 个 Key，此时数据持续流入 Master 的积压缓冲区（Backlog）。
  4. 恢复 Slave 连接，触发从节点向主节点发送 `PSYNC <master_replid> <offset>`。
  5. **断言核心指标**：
     * 读取 Master 的 `INFO replication`，断言 `sync_partial_ok` 计数器自增 1，而 `sync_full` 保持为 0。
     * 断言 Slave 的数据在短时间内与 Master 完全达到字节级一致。

---

### 3.3 功能三：Sentinel 故障转移与网络分区（脑裂模拟）

#### 3.3.1 业务功能背景
当主节点与哨兵发生网络隔离时，哨兵必须在预定超时（`down-after-milliseconds`）后完成客观下线认定，发起 Raft 风格的选主投票，并将某个从节点提升为新主节点。

#### 3.3.2 测试用例设计方案
* **测试用例实现逻辑**：
  1. 编排 1 主 2 从 + 3 哨兵集群。
  2. 通过发送 `DEBUG SLEEP 10` 命令让 Master 进入冻结挂起状态（模拟突发断网或真机宕机）。
  3. 轮询监控 3 个 Sentinel 节点的事件发布流（`SUBSCRIBE +switch-master`）。
  4. 断言 Sentinel 能够判定 Master 主观下线（`+sdown`），随后达成客观下线（`+odown`），选出新 Leader 哨兵并下发 `slaveof no one`。
  5. 唤醒原 Master，断言其能正确被降级为新主节点的 Slave，防止出现双写脑裂。

---

### 3.4 功能四：AOF 文件损坏与崩溃恢复容错断言

#### 3.4.1 业务功能背景
如果服务器在写入 AOF 磁盘文件的瞬间遭遇物理断电，文件末尾可能留有残缺的字节流。

#### 3.4.2 测试用例设计方案
* **设计方式**：
  1. 正常写入一批命令，触发 AOF 文件落盘。
  2. 测试脚本直接打开磁盘上的 `appendonly.aof` 文件，在文件尾部强制写入随机垃圾字节（模拟崩溃残缺帧）。
  3. 尝试重启 `redis-server`：默认应拒绝启动并输出错误日志。
  4. 测试程序调用 `redis-check-aof --fix` 工具自动修复文件。
  5. 重新启动服务，断言修复后的 AOF 能够被正确加载，且残缺之前的历史数据 100% 完整无损。

## 4. 自动化测试基础设施与 CI 质量保障

### 4.1 AddressSanitizer (ASan) & UndefinedBehaviorSanitizer (UBSan)
* **CI 编译配置**：启用 `make SANITIZER=address` 编译 Redis 二进制。
* **门禁规则**：在运行全量 Tcl 测试套件期间，任何微小的内存越界读写、Use-After-Free 或未定义行为，编译器注入的探针会立即拦截并以非零状态码终止进程，定位精确到源文件代码行。

### 4.2 Valgrind 内存泄漏扫描
* 针对长时间运行测试，将 `redis-server` 置于 Valgrind 虚拟机中执行，测试套件跑完后检查是否有任何未被释放的堆内存块（Definitely Lost / Indirectly Lost 必须为 0）。

## 5. 对复杂系统自动化测试设计的实战借鉴意义

* **针对分布式系统的拓扑测试脚本化**：对于涉及集群、主从、分片的分布式架构，自动化测试必须具备声明式编排多节点网络拓扑的能力。
* **故障注入不仅针对进程终止，还要针对“冻结”与“慢节点”**：在测试高可用时，挂起进程（`pause` / `freeze`）比直接 `kill -9` 更能测试出复杂的超时与状态竞争 Bug。
* **物理持久化残损与修复测试常态化**：任何带有 WAL（预写式日志）或文件持久化的系统，都必须在测试用例中人为制造“半写入（Half-written）”断裂文件，验证崩溃恢复逻辑。
* **C/C++ 及底层系统必须建立 Sanitizer 自动化常态化门禁**：逻辑测试全通过不代表无缺陷，内存安全探测工具必须与自动化回归测试紧密结合。
